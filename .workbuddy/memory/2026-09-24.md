### 机制要点（不要推翻）

1. **Terminal 状态 = sidecar，独立于 GameState**。`StoredRun` 新增 `terminal?: TerminalSidecar`（stage/version/transitions）。
   `ruleStateHash` 跨纯 presentation 转换字节相同（`UI04E_idempotency` 测试断言）。
   `state.ref` / `ui.ref` 完全未动；GameState 不增加 terminalStage 字段。
2. **Exactly-once by `terminalTransitionId`**。Receipt 检查**先于** stage drift 检查 ——
   否则 retry-after-post-commit-timeout 会误报 `terminal.stage_drift`。
   顺序必须是 ownership → reachedEnd → prior receipt → stage drift → fresh settle。
3. **`PostCommitTimeoutError` 必须映射为 typed retryable**。
   不能让平台超时以裸异常逃出；live service 捕获后抛 `TerminalFlowError(TRANSIENT, "terminal.post_commit_timeout", true)`，
   下一次同 id 调用经 exactly-once 路径返回 settled 结果。
4. **NEXT_LIFE 走 `generateServerDestinyOffer`，不要手工拼 offered run**。
   CONTENT01 的 progression.v1 用 innateProfile 模式，必须让 destiny-offer 生成器决定 destinyIds/innateProfiles。
   新生命是独立 document，老 run 不可变。
5. **NEXT_LIFE 的新 runId 用 `run-${runIdSeedFor(playerId, nextBootstrapId)}`**。
   确定性派生，retry 才能 recover 到同一文档。
   receipt 自身存 `nextBootstrapId` / `nextRunId`，cold start 后 retry 直接拿到。

### 4th RPC（advanceTerminal）

- request: `{ runId, terminalTransitionId, expectedTerminalStage, action }`
- response: `{ ok, terminalTransitionId, stage, version, nextBootstrapId?, nextRunId? }` 或 `{ ok: false, terminalTransitionId, error: { code, messageKey, retryable } }`
- action 严格四值（前向图）：`advance-to-life-book` / `advance-to-rebirth-result` / `advance-to-next-life`
- expectedTerminalStage 是 stale-client 护栏：retry 永远带**发送前**的 stage，settled 后 stage 已前进；
  prior receipt 检查必须先于 stage drift 检查。

### 踩坑记录

- **arttool 不支持 `import { X as Y }`**：`server/src/live-service.ts` 用 `import { advanceTerminal, ... }` 必须省略 `as alias`，
  工具拒绝这种 binding（`unsupported import binding`）。
- **CloudBase harness snapshot 是 copy 不是 live view**：
  `database.snapshot().get(...).set(...)` 写入的是 snapshot 副本，对实际 collection 无效。
  必须给 harness 加 `seedDoc(name, id, data)` 直接写 committed collection。`tests/ui04d.test.mjs` 仍 20/20 ——
  harness 签名 additive，没破坏既有。
- **CONTENT01 是 innateProfile 模式**：测试 seeding 时不能只 patch `destinyIds`，必须保留 service.createRunOffer
  生成的 `innateProfiles`。`seededState = { ...beforeDoc.state, run: { ...beforeDoc.state.run, age, maxAge } }`
  即可，age/maxAge spread 不会破坏 offer。
- **`seedDoc` 必须用 `createCommandLog(seededState)`**，不能用 `{ baseSequence: 0, entries: [] }` ——
  CommandLog 需要 schemaVersion/rulesVersion/contentVersion/runId/playerId 五个 metadata 字段，
  否则 `executeLoggedCommand` 走 `validateCommandLog` 抛 `PersistenceError("persistence.invalid")`。
- **`destinyIds` 必须是 3 个**：`createOfferedRun` / `validateGameState` 强制 `destinyIds.length === 3`。
  NEXT_LIFE 用 `generateServerDestinyOffer` 走 CONTENT01 自身 progression 模式（产生 innateProfile offers），
  不要手填 `["destiny.next-life"]`（只有 1 个，会过不了 validateGameState）。
- **stage drift 检查必须在 prior receipt 之后**：retry-after-post-commit-timeout 的 expectedTerminalStage
  必然是 stale（发送前的 stage）。prior receipt 是 "this id 已经 settled" 的唯一权威信号，
  先查 receipt 再查 drift，retry 才能 recover；否则误报 `STATE_CONFLICT`。
- **PostCommitTimeoutError 必须 typed retryable**：不能裸异常逃出 live service。映射到
  `TerminalFlowError(TRANSIENT, "terminal.post_commit_timeout", true)`，client retry 走 exactly-once 路径。
- **terminal-flow.js 不应放 `TERMINAL_TRANSITIONS_COLLECTION` 常量**：那是 CloudBase store 的职责。
  测试用 `stripJs(store)` + 断言 `storeSource.includes("TERMINAL_TRANSITIONS_COLLECTION")`。
- **stripJs 必须用于"是否引用了 forbidden token"判断**：直接 `store.includes("where")` 会命中注释里的"`.where(`"。
  audit 也是 stripJs 的（assertCloudCommonJs 里）。
