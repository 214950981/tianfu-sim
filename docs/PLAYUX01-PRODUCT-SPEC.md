## 0. 决策权及证据边界

此文档是产品设计合同，不是让 WorkBuddy 自行设计的讨论提纲。WorkBuddy 的职责是核对现有契约、按此设计实现、给出技术映射和测试证据。如在技术上无法同时满足，应返回明确的 CONTRACT_CONFLICT / BLOCKED 及最小替代方案，不得自行改变玩法方向、虚构事实、改变奖励或偷偷删减验收范围。

已核实的代码事实：
- Core 的 CHOOSE_ACTION 时间成本：cultivate=3，travel=2，worldly=1，pursuit=1。保持原数值，不得以 UX 为由偷偷改平衡。
- Director 的 P2 onboarding 候选目前未按用户行动过滤，P5 根据 action 等索引取候选，P6 ordinary 是跨行动共用池；actionAffinity 目前提供加权，并不保证行动语义相符。
- Content01 的多数普通场景统一追加固定尾句。非风险/非因果场景多数沿用 engage、consider、leave 三个选项，分别默认主要效果、修为增长、灵石增长；这会产生“道路选择却给灵石”等语义冲突。
- run.events.history 目前主要保留 eventId、nodeIndex、resultTier；公开终局 lifeBook、公开可见人物和 Build 有现成的服务端投影，但不能假设过去每个 choiceId、每项属性变化都已被存档。
- 客户端现有 LIFE_BOOK 只把公开数据展示成计数，ENDING 也只拼固定句子；死亡原因原始标识未统一汉化。
- 五张真机截图只证明这些问题在至少一条实机链路出现，不证明所有存档都必然不一致。

## 1. 玩家流程，必须逐屏实现

主流程：
RUN_HOME 行动选择 → EVENT/SPECIAL_NODE 展示具体处境 → 选择某个具体行动 → 已验证的选择结果和公开变化 → 返回 RUN_HOME → 可从生平录检索此次经历 → 在终局解释本世结束原因 → 人生书回顾真实关键转折 → 继续现有转生链。

严格约束：
- 在结果页未完成展示之前，不要因为服务器已经结算就立刻跳过结果页。结果页为同一条权威命令的只读回顾，返回主页不再次提交命令。
- 服务端权威态、期望版本、幂等命令 ID、RNG、Director 优先级、玩家身份、已存盘事实都不可绕过。
- 游戏结果以实际可证明的公开值为准。没有结算或者没有公开依据时，不可写“获得、损失、结识、发现”。
- 不泄漏随机数、概率、隐藏因果和 NPC 隐藏信息。
- 新表现层应处理“服务器刷新/断线/旧存档没有结果摘要”情况，不重复给奖，不出现假结果。

## 2. 四种行动设计：命名、诉求和候选规则

| 按钮 | 玩家真正发出的意图 | 当前时间成本 | 主事件范围 | 允许的跨行动情形 |
|---|---|---:|---|---|
| 闭关 cultivate | 消耗时间修炼、稳定气机、尝试突破 | 3 | 修炼、功法、瓶颈、心性、修炼风险 | 牵连人物或因果的修炼事件 |
| 游历 travel | 探访世界、沿途发现与遭遇风险 | 2 | 山路、遗迹、旅途、陌生人与野外危险 | 途中结识的人可能引出入世或追索 |
| 入世 worldly | 与人物和势力发生社会互动 | 1 | 市集、交易、交往、任务、人情、宗门 | 与特定人物约定可延伸为追索 |
| 追索 pursuit | 沿已知线索或因果追查 | 1 | 旧痕、线索、失踪者、秘密、前次事件回响 | 有已知人物/因果时可跨地域追查 |

决定如下：
A. **P2 首次引导**必须尊重本次 action。修炼不能进入山路教学，追索不能进入早市教学；当前动作没有 onboarding 候选时，要有确定、可解释的回退，不得从其他动作随意抓一条引导剧情。
B. **P6 普通兜底**不能继续无条件在四种行动之间混用。为普通场景补上被产品确认的适用行动标签，再以 action 选择语义匹配候选。允许明确标注两个及以上适用行动的合理跨行动事件；不允许为提高可达率而把所有普通事件标注为四种行动通用。
C. 保留 P3 已成熟 Cause 回响及 P4/P5 的优先级、NPC 连续性、主要事件间隔等旧约束。强因果事件确需越过当前行动时，显示“旧事牵动”等可信的上下文，而不是把它伪装为普通随机遇事。
D. 当一个动作没有合适候选时：采用现有合法机制产生清晰的无收获/行动落空反馈，或返回明确的不可用状态；**不得**制造虚假事件、用未注册 EventId 填坑、绕开 Registry、或用不匹配动作的事件充数。确有内容覆盖缺口应在报告中列明，而非悄悄改变概率。
E. 不调整前述 3/2/1/1 基础年数，不直接更改原 RNG stream draw 数；如候选改动导致固定种子选择变化，只允许由确定性候选集变化引起，并以固定种子重放验证。

四个必须展示的代表性场景：
- 闭关：content01.onboarding.first-breath 或 content01.onboarding.quiet-retreat；玩家读到修炼过程中实际发生的事，选项围绕继续行功/调整方式/及时收功。
- 游历：content01.onboarding.mountain-road；玩家有具体去向、选择道路的利弊与后果，不能无缘无故获得灵石。
- 入世：content01.onboarding.market-choice，或具已注册商人参与者的 content01.ordinary.market-bargain；选择围绕谈价、往来、拒绝交易，结果与实际货币或公开关系变化相符。
- 追索：content01.onboarding.old-trace；玩家知道调查对象、眼前证据以及下一步方向。若没有合法可记录的新线索，不显示“找到线索”的虚假结果。

## 3. 事件文案与选项：禁止全能模板

标准事件卡固定结构：
① 来源标签：本次动作、已知公开位置/人物/旧事原因（有则显示；无则省略）。
② 标题：一句具体的事件名称。
③ 场景：2 至 4 句可理解的具体事实：发生了什么，玩家为什么在此，哪些信息可见，冲突是什么。
④ 2 至 3 个具体选项：用动词命名，指向可辨认的不同行为；只给服务器已公开的风险/条件提示。
⑤ 按钮“作出选择”可保留，但每个选项文案必须表达自己做了什么，不能再全是通用的“顺势而行/停步细看/见好便收”。

禁止：
- 一律追加“你可以顺势而行……留在往后的年月留下形状”等相同空泛尾句。
- 用“依此磨炼、见好便收、承担此险”作为与场景无关的默认选项。
- 给没有交往对象的孤身山景选择添加人物关系奖励。
- 说“暂避风险”却发放无来源灵石；说“追查真相”却只给纯修为奖励而没有能被玩家理解的修炼过程；没有来源时不伪造收益。
- 仅把 UI 换文案、却不核对该 choiceId 的真实 outcomes.effects。

**产品样例 1：偏僻岔路（content01.build.fortune.fork）**
- 场景文案示例：你沿熟路赶往山外，岔路旁却留下新鲜蹄印。熟路有行人，能按时抵达；偏路通向林深，看不清尽头。这里真正要决定的是行程与未知机会，而不是抽象的“磨炼”。
- 候选选项意图：循蹄印进入偏路；登高观察后再决定；放弃偏路沿熟路赶路。
- 实施规则：每条选项必须对应可验证的已注册效果、公开成本或风险；如果现有效果无法解释为上述动作，优先使用同类已受支持的效果做**小范围、显式、带测试的 Content 修订**，不得给三个选项随意派发原模板奖励。实际效果、选项文字、验收样例写入同一张对照表，供 Controller 审核。
- 不准把“选择偏路”写成必然遇到仙缘，除非注册的效果和公开状态真的证明发生了仙缘。

**产品样例 2：山色（content01.ordinary.mountain-view）**
- 这是典型的游历风景/调息场景；不能作为“追索线索”的普通随机场景。
- 可以作为旅途轻事件保留沉浸感，但必须有合理的“停留调息/观路辨向/继续上路”差异；未产生数值或事实变化时，结果诚实写“此行没有明显收获”，不可虚构秘密或道具。

**产品样例 3：闭关初息 / 入世早市 / 追索旧痕**
- 各选择至少包含一个明确推进对应行动目标的方案、一个审慎方案、一个撤离/延期方案；每个方案对应可核对的已注册收益/成本/风险，实际没有对应效果时需局部调整或者如实标记暂不支持。
- 风险事件保留真实失败/代价分支，不可将危险选项一律写成稳赢。
- 与 NPC 和 Cause 相关的事件，应展示公开身份或已知关系，不能泄漏隐藏演员状态。

实施顺序：先按分类消除共用模板的问题，再实现每类至少一个高质量的完整范例，再扫描剩余可达 Content01 场景。报告剩余场景数量和原因。不得以只有四个范例可玩就宣称全量故事质量 PASS。

## 4. 选择后的反馈屏，必须完整闭环

EVENT 的选项一经服务器确认成功，先出现一个独立的“本次结果”区域，包含：
- 发生了什么：一句基于真实结果的具体叙述；公开结果不足时，退为保守事实“本次选择已完成”，不可编造过程。
- 确认的变化：修为、灵石、寿元/年龄、已公开状态变化、人物关系、明确因果、公开道途进度，按实际变化显示；使用“修为 0→150 (+150)”这类对照。变化为零不写收益，不展示未知项。
- 尚未解决：仅对服务器公开、仍存在的线索、因果、风险显示；否则不展示这一栏。
- 回到在世：只负责关闭结果区域，不能再次 submit 命令。

获取数据优先级：权威结算回执中已公开的结果 > 同一命令提交前后的权威 PublicView 差异 > 最小、兼容的增量公开投影。不能拿客户端 UI 设想的 reward 当做真实值。
网络失败、冲突刷新、重试、重复 commandId：不显示假成功，不重复结算，同一成功操作至多展示同一份结果。跨会话恢复若结果来源不可靠则不要自动恢复旧结果叙事。

## 5. 生平录：活着时的“可追溯个人日志”

定位：玩家随时打开，回答“我在什么阶段经历过哪些公开事件、作过哪些已记录选择、留下了什么影响？”。
结构：
- 时间顺序：公开年龄或节点 → 行动来源（可确认才显示）→ 事件名 → 实际选择（有已存公开 choiceId 才显示）→ 已证明的简短结果。旧档若无选择字段，显示“此前选择未记录”，不可倒推。
- 因果：只列已公开的未解/已解决因果以及来源事件；隐藏因果绝不泄漏。
- 人物：已结识者及已公开关系变化；不许列未相识 NPC。
- 道途：中文名称 + 潜藏/萌芽/成形等准确阶段。不是把潜藏资质直接计算为“已修成的两条道途”。

具体缺陷：content01.*.history 是当前 340 键翻译表未必拥有的派生历史键；build.build.fortune.latent 也是 Build 标签，不属于 Content01 事件标题翻译表。
修复要求：优先根据原 eventId 查真实 EventDefinition.titleKey 和 Content01 中文文案；仅在公开内容提供 summary 时显示可信摘要。Build 阶段依赖 Build pack 的权威 displayName/stage 映射，不能靠截断内部 ID 猜中文。
不得把同一条事件的标题、历史伪键、结果键累积成三个不同经历。

## 6. 终局与人生书：一个事实源，两种用途

ENDING 的职责是回答：这一世何时结束、是什么已知直接原因导致结束、你留下了什么可验证的结果。
建议首屏顺序：
- 标题：“此生已终”
- 身份：未名、寿命/结束年龄、最终境界
- 原因：例如“伤势过重，未能熬过此劫”（仅在实际 deathRecord 支持时），可展开已公开的风险来源。不能将 death.death.injury 或 threat.critical-injury 原封不动打印。
- 已知事实摘要：经历、认识的人、已成形道途、公开因果；由 LIFE_BOOK 同一权威基底计算，不能前后不一致。
- 按钮：“回顾此生”。

LIFE_BOOK 的职责是回答：这一世**如何走到这里**，区别于活着时的流水账。
建议结构：
1. 起点：真实选择的命格、初始公开身份，没有资料就省略。
2. 若干关键转折：从已记录的事件中按可解释的显著性与事件时间排序，至少对有数据的玩家展示真实事件名、结果，说明为何可算转折；不记录 choice 时不可假装玩家曾怎样选择。
3. 结识的人与道途：仅公开已认识 NPC、实际进度、真实成形/潜藏区别。
4. 终局：结束时间、直接死因、公开相关事件/风险、未竟因果。
5. 转生：已有合法继续下一世的入口。不可把“转生后继承某物”写成既定事实，除非结算已给出。

严格检查图4与图5同一世 ENDING 显示 0/0/0，而 LIFE_BOOK 显示 11/4/2：
- 先用确切的存档投影及 stage 比较复现。检查 terminal sidecar、buildPublicTerminal 与客户端 stage 取值/默认值是否一致。
- 修复必须有测试证明同一 runId 同一批公开事实在 ENDING、LIFE_BOOK、REBIRTH_RESULT 对应共同指标保持一致。
- 若“道途数量”的统计定义不同，明确定义并使用不同标签。不可把 latent 误标为 formed，或者把 people encountered 与 people known 混为一谈。
- 未复现时写出实际观测、可疑路径和残余风险，不得凭推断修改数据库数据。

## 7. 可观察层中文与保守降级

映射范围至少包括截图见到的：
- death.death.injury
- threat.critical-injury
- content01.build.fortune.fork.history
- content01.ordinary.mountain-view.history
- build.build.fortune.latent

优先采用源域已有中文展示名、Build 包元信息、已知 death category/source 组合来形成中文；不能仅做一个任意字符串替换表以掩盖真实字段错误。对其他合法注册的死亡/终局状态做键集合校验。
未知键要在开发测试中被抓到；正式面向玩家时保守显示“详情暂不可用”，而不是输出原始编码或者编造解释。保留开发追踪能力，不泄漏内部敏感信息。

## 8. WorkBuddy 按以下顺序施工，但只交付一个任务

阶段 A：建紧凑“产品行为映射表”（4 行动 × 代表事件 × 每个 choiceId × 实际 effects × 公开可见结果），在 Git 提交的设计说明内列明。确认技术可以实现本规范。
阶段 B：Action → Director → Content 语义匹配和 4 条实际可执行样例。保持原 Cause/NPC 优先级及确定性。
阶段 C：选择后的权威反馈屏及必要的最小公开结果通道，验证重试不会重复结算。
阶段 D：生平录、终局、人生书和公开历史键、死亡原因中文。进行计数一致性测试。
阶段 E：一次集中跑定向测试，再提交 wb-PLAYUX01 + LAST_RESULT。若有服务端代码变化，必须报告云端仍为旧版本，禁止未经批准部署，不能把静态测试写成实机 PASS。

不得中途转为 PLAYUX02、要求 Controller 对一个小文案点单独开任务，也不得频繁跑全仓库测试。允许 A-E 在一个工作分支内部多次小提交，Controller 只做最后一次独立验收。

## 9. 验收矩阵（缺任何一项不能声称完整 PASS）

| Gate | 明确通过标准 |
|---|---|
| 动作区分 | 固定初始状态分别点击四个行动，匹配的 P2/P5/P6 事件具有真实语义；不出现追索抽出“山色”这类无由来普通事件 |
| 选项语义 | 偏僻岔路选项分别做什么、对应 effect 和真正结果有一一对照；不存在“跑路就送钱”的奖励 |
| 内容风格 | 所有修过的可达事件不再含统一空泛尾句；四条代表场景的选项全为场景专属文字。扫描并披露剩余模板场景数 |
| 结果反馈 | 每次完成后清楚显示真实公开变化；无变化就说无变化；刷新与重复提交不多发资源和故事 |
| 生平录 | 本次事件可按时间追溯且中文可读；旧档不存在的 choice 不能凭空出现；不再有 .history、build.*.latent 生硬键 |
| 终局 | 必须解释已知死亡原因，0/0/0 与 11/4/2 的同存档冲突复现后被解决，或提供可复核的不同定义及依据 |
| 人生书 | 对有历史事件的存档显示公开真实转折，不只报总数；死亡与人生终点可理解；不披露未公开秘密 |
| 安全回归 | 涉及的 deterministic replay、幂等、Cause 绑定、风险与死亡、终局 sidecar、Next Life 有定向正向和负控测试 |
| 范围 | 不修改 main、不偷跑云函数部署、不清理存档、不跑 600 局、不启动后续任务；所有真实测试及未覆盖项如实披露 |

## 10. 不可由 WorkBuddy 自主变更的产品决定

- 四种行动的玩家意图及时间成本不能重新定义。
- 不把所有事件强行分到互不联系的四个池，合理的 NPC/因果跨行动必须存在且能解释。
- 不用随机话术包装数值结果；有史可查才讲，有公开证据才给奖励。
- 生平录是活档，人生书是死后回顾，终局是死因和落幕。三者不能都是数字统计页。
- 宁可把少量无法可靠展示的字段保守隐藏，也不能用文案杜撰经历。
